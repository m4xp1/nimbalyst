# Задание агенту Nimbalyst: приёмка форка 0.79.1+m4xp1.1

Это инструкция для отдельной сессии после ручной установки владельцем. Ответ и отчёт — по-русски. Цель: проверить установленный продукт и вернуть воспроизводимые свидетельства Codex. Не исправляй код и не объявляй PASS без наблюдения.

## Границы

Работай только в новом временном проекте Nimbalyst-search-smoke-0.79.1-m4xp1.1. Не используй helper, helper-sdlc, ai-studio или другие частные vault для индексации/поиска. Если активный проект другой, сначала предложи владельцу открыть отдельный тестовый каталог и запустить сессию агента в нём; до этого поиск не выполняй.

Разрешены 4 искусственных Markdown-документа: три файла ниже и один факт, создаваемый remember. Используй уже настроенный OpenAI без смены модели и без передачи ключа в чат. Не скачивай модели. Всего не более 10 поисковых запросов через Memory (UI и MCP суммарно). Индексация этих коротких fixtures также может обращаться к OpenAI; повторные Rebuild и полная индексация других проектов не разрешены. При исчерпании бюджета запросов останови поиск и сохрани отчёт.

## Подготовка

1. Проверь About: должно быть 0.79.1+m4xp1.1. Запиши Windows, дату, способ установки и наблюдаемую версию.
2. Перечисли фактически доступные Memory MCP tools. Не выдумывай namespace или параметры. Вызови доступный status и проверь, что root относится именно к тестовому проекту. Если инструмента нет или проект не совпадает — отметь BLOCKED, не подменяй проверку обычным grep.
3. Создай следующие три файла (каждый содержит заголовок и указанный текст):

- docs/ru-release.md — «Проверка установщика». Перед установкой Windows x64 вычисляют SHA-256 загруженного EXE и сравнивают со значением из SHA256SUMS.txt. Контрольный маркер: янтарныймаяк.
- docs/en-review.md — «Review policy». A reviewer approves changes before publication. Review decisions are recorded and the prior release remains available. Unique marker: reviewcomet.
- research/fork-checks.md — «Ручная сборка форка». После уведомления об upstream обновлении пользователь собирает форк вручную. Автоматические скачивание и установка отключены. Контрольный маркер: лазурныйкомпас.

4. Настройки Memory должны показать фактически активный OpenAI профиль. Не включай индексирование AI sessions для теста. Дождись конца первоначальной индексации; зафиксируй status и ошибки.

## Источники и обновления

- В Additional Markdown sources добавь research/ и перекрывающий research/**/*.md. Preview должен показывать fork-checks.md один раз и причины служебных исключений. До Apply никаких изменений правил не заявляй выполненными.
- Apply должен включить файл в индекс с классом custom; встроенные docs остаются docs. Сохрани свидетельство UI и status. Настройки источников доступны только панели, их отсутствие среди MCP tools ожидаемо. Если агент не может действовать в UI, попроси владельца выполнить шаг и пометь его как ручной.
- Перезапусти приложение и проверь сохранность правил/индекса.
- Позже измени маркер research/fork-checks.md на лазурныйкомпасновый, дождись обновления без Rebuild.
- После поисковых проверок исключи research/fork-checks.md через настройки: файл остаётся на диске и исчезает из Memory. Сними исключение; затем удали только этот тестовый файл и проверь удаление из индекса без перезапуска. Не удаляй весь каталог проекта.

## Запросы: максимум 10 суммарно

Ожидаемый документ фиксируй ДО запроса. Запиши источник, headingPath, первые 3 результата, signals/provenance если доступны, фактический ответ и ошибку.

1. UI: янтарныймаяк → docs/ru-release.md первым.
2. MCP: reviewcomet → docs/en-review.md первым.
3. UI: Как убедиться, что скачанный установщик не повреждён? → раздел «Проверка установщика» среди первых 3.
4. MCP: How should I verify the downloaded Windows installer integrity? → тот же русский раздел среди первых 3.
5. MCP: лазурныйкомпас → research/fork-checks.md первым.
6. После изменения файла: лазурныйкомпасновый → актуальный текст, прежний текст не выдаётся как текущий.
7. После исключения: лазурныйкомпасновый → исключённый документ отсутствует.

Оставшиеся до 3 запросов можно использовать для одного воспроизведения сбоя. Не расходуй их на бессистемные переформулировки. Проверяй найденный текст через доступный read/expand, а не только заголовок результата. Такие чтения не заменяют поиск. Семантические запросы проверяют модель; keyword и semantic+keyword — разные свидетельства.

Отдельно используй фактически доступные remember/recall: создай единственный четвёртый искусственный документ-факт «Журнал тестового проекта помечен словом ёлочкаконтроль», затем recall(query=елочкаконтроль). Ожидается этот факт. Сам recall не требует embeddings; remember может вызвать индексацию. Не обещай отсутствие любых фоновых расходов по этому наблюдению.

## Интерфейс и статусы

- Мишени возле FILES нет; клик по имени ru-release.md в строке пути раскрывает дерево и выделяет файл.
- Клик docs показывает содержимое docs. В меню можно перейти вверх/внутрь папки, открыть файл, двигаться стрелками, закрыть Escape и кликом снаружи.
- Если доступны создание карточки и связь с существующим Markdown, используй docs/ru-release.md: изменение в CONTENT должно сохраниться в файл и появиться в открытой вкладке. Проверь повторное открытие и сохранение frontmatter. Затем измени файл извне при чистом редакторе; убедись, что карточка обновилась. Не проверяй конфликт записи на настоящих документах. Если доступного пути нет, пометь NOT VERIFIED.
- Зафиксируй состояние индекса, обнаруженные/обработанные/сохранённые файлы, vectors и активность наблюдения. 100% относится к сохранённым chunks; не трактуй как охват всего workspace.
- Refresh должен только обновлять статус. Без сетевой трассировки не утверждай, что доказал ноль API-вызовов: механика проверена автоматическими тестами.
- Не отключай сеть и не меняй действующий ключ ради искусственного 401/429. Обработку таких ошибок проверяли fake-provider тесты; естественную ошибку зафиксируй без ключей и сырых ответов. Retry/очередь восстановления не входят в выпуск. Миграцию старой БД этим новым проектом не проверяешь.

## Отчёт для Codex

Сохрани REPORT.md в тестовом проекте после окончания поисковых проверок; этот отчёт не добавляй в источники. Для каждого сценария: ID; PASS/FAIL/BLOCKED/NOT VERIFIED; ожидаемое; фактическое; точные шаги; query; root; результаты/heading/signals; свидетельство UI или MCP; повторяемость.

В начале отчёта: версия About, Windows, дата, фактический embedding-профиль, правила источников, использованные tools, число поисковых запросов. В конце: выполненные проверки, непроверенные границы, оставленные fixtures и итоговый вердикт. Не включай ключи, токены, Authorization и полный сырой ответ провайдера. Приложи отчёт владельцу для передачи Codex. Codex определит, нужен ли патч, по доказанному воспроизведению.
